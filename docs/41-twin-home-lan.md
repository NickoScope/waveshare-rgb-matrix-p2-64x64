# Твин в домашней сети: свой IP, своя MAC-идентичность, имя с префиксом TWIN-

## 0. Итог

1. **Рекомендация.** Мост vmnet на Wi-Fi через `socket_vmnet` v1.2.2, режим `bridged`, интерфейс `en0`. Демон работает от root под launchd. Движок подключается к его Unix-сокету без sudo. Твин получает адрес от DHCP роутера eero в 192.168.4.0/22, как настоящее устройство. HA и другие хосты сети ходят на этот адрес напрямую, `discover.py` находит твин по `mac=` в mDNS TXT.
2. **Предел, который нельзя обойти по Wi-Fi.** В эфире и в ARP-таблицах за IP твина будет стоять MAC Wi-Fi этого Mac (`d2:bf:…`). Это MAC-NAT ядра XNU. Он включается сам, когда в мост добавляют Wi-Fi-станцию (xnu-12377.121.6 `bsd/net/if_bridge.c:2966-3011`, verified). Собственный MAC твина `02:54:57:49:4E:01` виден в DHCP (`chaddr` и option 61) и в mDNS TXT. Значит, аренда и резервирование на роутере привязаны к твину, а не к Mac. Полностью свой MAC на проводе даёт только проводной адаптер (запасной путь №1).
3. **Порядок работ.** Сначала владелец один раз ставит демон (§3). Затем проверка A0 и A1 (§7): мост поднялся, eero отвечает на DHCP. Код движка пишется только после этого. Если A0 или A1 не проходят, переходим к запасным путям (§5).

## 1. Поправки к постановке и расхождения исследований

- `en0` — это **/22**, а не /24: маска 255.252.0, broadcast 192.168.7.255. Подтвердили все три исследования (ifconfig, `ipconfig getpacket`), verified.
- Исследование `engine` пишет `own_mac: true` для моста, исследование `vmnet` пишет `false`. Правильный ответ — **частично**, как в п. 2 итога. Тот же исход у варианта `vmnet.framework` напрямую.
- Где в тарболе лежит plist. `engine` пишет «likely», `vmnet` проверил `tar tzvf` на самом релизе. Путь `opt/socket_vmnet/share/doc/socket_vmnet/launchd/` — verified.
- **Новое, проверено мной.** Прошивка отправляет DHCP option 61 (client-id). В `sdkconfig` фреймворка Arduino-ESP32 2.0.17 (`framework-arduinoespressif32` 3.20017, platform `espressif32@6.12.0`) стоит `# CONFIG_LWIP_DHCP_DISABLE_CLIENT_ID is not set`, а `lwipopts.h:271` поясняет: при 1 option 61 не добавляется. Сам `dhcp.c` лежит в прекомпилированной библиотеке и не прочитан, поэтому уровень **likely**. Следствие по RFC 2131 §4.2: сервер ключует аренду по client-id (`<MAC>:01`), а не по `chaddr`. Поэтому аренда останется за твином, даже если будущая macOS включит `net.link.bridge.use_dhcp_xid=1` и начнёт переписывать `chaddr`.
- **Новое, проверено мной.** Если в сети две панели, `apc-ota/tools/agent/panel.py:300-301` при вызове без `--panel`/`--mac` бросает `ChoiceNeeded`, а не берёт первую попавшуюся. Пока твин в сети, OTA не уйдёт не туда. Но все автоматические вызовы, включая OpenClaw, должны явно передавать `--mac 90:E5:B1:D2:0E:2C`. Иначе они будут падать с этой ошибкой.
- **Новое, проверено мной.** HA-discovery прошивки строит `node_id` из трёх последних байт MAC (`src/climate/climate.cpp:117`). Если у твина включить MQTT, в HA появится отдельное устройство (`…_494e01`). С сущностями настоящей панели оно не пересечётся. `clientId` тоже разный: `apc-494E01` (`mqtt_bus.cpp:192`).

## 2. Что получится с мостом `socket_vmnet bridged en0`

| Где смотреть | Что видно | Основание |
|---|---|---|
| Аренда DHCP в eero | IP из 192.168.4.0/22, hostname `TWIN-…`, client-id/`chaddr` = MAC твина | XNU MAC-NAT ставит broadcast-флаг и не трогает `chaddr` при `use_dhcp_xid=0` (sysctl на этом Mac, verified). Option 61 — likely, см. §1 |
| ARP у HA и роутера | IP твина → MAC Wi-Fi Mac | if_bridge.c 9356-9359 (verified), socket_vmnet #32 (verified) |
| mDNS | `TWIN-….local`, `_http._tcp`, TXT `mac=02:54:57:49:4E:01` | network.cpp 232-236 (прошивка) |
| Входящий unicast из LAN | доходит, пока жива запись MAC-NAT (20 мин тишины → запись пересоздаётся при следующей передаче твина или его ответе на ARP) | if_bridge.c 376, 7584 (verified). **Замер 29.09:** с nickol (RPi5, 192.168.4.37, Wi-Fi) после 21 и 42 мин без входящих запросов: ARP-запись nickol STALE, `/api/info` — HTTP 200 за 0,054 и 0,049 с. Справочно: по одному прогону, при этом MQTT двойника работал (его исходящий трафик мог держать запись) |
| Mac → твин | по исходникам ядра должно работать | if_bridge.c `bridge_member_output`; **не проверено**, есть жалобы UTM на macOS 15 |

**Главный риск на этом железе.** Mac17,9: M5 Pro и Wi-Fi-чип Apple N1. На этой связке `ifconfig bridge0 addm en0` падал с «Operation not supported on socket». По сообщениям пользователей, починено в 26.6 / 26.6.1 (UTM #7658, likely). Здесь стоит 26.6.2, и `vmnet_copy_shared_interface_list()` отдаёт `en0` (verified). Но сам мост без root не проверить, поэтому A0 — первый шлюз.

## 3. Что владелец запускает один раз и зачем

Зачем нужен root. vmnet в режиме bridged требует root или entitlement `com.apple.vm.networking`. Apple выдаёт его только разработчикам виртуализации (Apple docs, README socket_vmnet FAQ, verified). Поэтому привилегию держит маленький демон, а движок остаётся непривилегированным. Сокет демона создаётся как `root:staff 0770` (main.c 395-411, cli.c:23, verified), а пользователь `apple` входит в `staff`. Kext не нужен. sysctl, firewall и настройки сети не меняются.

Ставить из релизного тарбола, а не через Homebrew. README (строка 194) пишет, что бинарник Homebrew «can be replaced by any user in the admin group», а он запускается от root.

```bash
cd ~/Downloads
curl -OSL https://github.com/lima-vm/socket_vmnet/releases/download/v1.2.2/socket_vmnet-1.2.2-arm64.tar.gz
gh attestation verify --owner=lima-vm socket_vmnet-1.2.2-arm64.tar.gz      # подлинность сборки
sudo tar Cxzvf / socket_vmnet-1.2.2-arm64.tar.gz opt/socket_vmnet           # root-owned /opt/socket_vmnet
sudo mkdir -p /var/log/socket_vmnet                                         # на всякий случай: создаст ли launchd каталог сам — не проверено
sudo cp /opt/socket_vmnet/share/doc/socket_vmnet/launchd/io.github.lima-vm.socket_vmnet.bridged.en0.plist /Library/LaunchDaemons/
sudo launchctl bootstrap system /Library/LaunchDaemons/io.github.lima-vm.socket_vmnet.bridged.en0.plist
sudo launchctl enable system/io.github.lima-vm.socket_vmnet.bridged.en0
sudo launchctl kickstart -kp system/io.github.lima-vm.socket_vmnet.bridged.en0
```

Результат: демон `--vmnet-mode=bridged --vmnet-interface=en0`, `RunAtLoad` + `KeepAlive`, сокет `/var/run/socket_vmnet.bridged.en0`. Лог пишется в `/var/log/socket_vmnet/bridged.en0.stderr`. Plist прочитан, verified.

Выключить, когда твин в сети не нужен, и удалить:
```bash
sudo launchctl bootout system /Library/LaunchDaemons/io.github.lima-vm.socket_vmnet.bridged.en0.plist
sudo rm /Library/LaunchDaemons/io.github.lima-vm.socket_vmnet.bridged.en0.plist
sudo rm -rf /opt/socket_vmnet /var/log/socket_vmnet
```

Необязательно, без sudo:
- Проверить в «Системных настройках → Wi-Fi → Подробнее», что «Частный адрес Wi-Fi» стоит в режиме «Фиксированный». Для WPA2+ это режим по умолчанию (Apple Support 102509). В режиме «Меняющийся» MAC в ARP-записи твина будет меняться раз в две недели. На аренду это не влияет.
- После первой аренды можно зарезервировать адрес в приложении eero. Разрешит ли eero резерв для клиента, у которого `chaddr` и client-id не совпадают с MAC в эфире, **не проверено**: страницы поддержки eero отдавали 404/502. Без резерва адрес ищем по MAC через `discover.py`, так же как у настоящей панели.

## 4. Что делаем мы («выложить патчем в нашем репозитории»)

### 4.1 Движок (`~/twin/esp32sim`, отдельный worktree `nickoscope/bridge`)
- `esp-soc/src/net/vmnet.rs` (только Unix, для wasm заглушка), около 170 строк.
  - `UnixStream` к пути из `--net bridge:PATH`.
  - **Читатель** — отдельный поток, который постоянно вычитывает сокет в ограниченный канал; при переполнении кадр отбрасывается и считается. Демон пишет клиентам блокирующим `writev`, и один нечитающий клиент останавливает всех (socket_vmnet #173, открыт, verified).
  - **Писатель** — тоже отдельный поток с ограниченным каналом, чтобы остановившийся демон не заморозил эмуляцию.
  - Кадр отправляется одним `write`/`writev`: `u32` big-endian длина + Ethernet без FCS, не больше 64 КиБ. Демон читает заголовок и тело по одному `read()` и проверяет длину живым `assert` (main.c 551-575, в Makefile нет `NDEBUG`, verified).
  - **Фильтр приёма обязателен.** Демон рассылает всё всем клиентам (main.c 169-196, verified), а у эмулированного MAC адресного фильтра нет (bus.rs 582-586). Пропускать только DA = MAC станции (узнаётся по SA исходящих кадров, запасное значение — `--mac`), broadcast и multicast.
  - Переподключение с задержкой на EOF/EPIPE: демон перезапускается после сна или переподключения Wi-Fi (#130).
  - Счётчики: `rx_ok`, `rx_filtered`, `rx_dropped`, `tx`, `tx_dropped`, `reconnects`.
- `net.rs`, около 25 строк. В режиме bridge `handle()` отправляет кадр как есть: DHCP-сервер, ARP-прокси, DNS, NTP, ICMP и NAT `VirtualNet` обходятся. `poll()` берёт из канала ограниченную пачку кадров.
- `wifi.rs`, около 15 строк.
  - Beacon задерживают только стоящие в очереди management-кадры. Сейчас любой кадр в очереди глушит beacon (wifi.rs 162-172), а через 6 с без beacon ESP32-станция отваливается (esp_wifi.h 1138-1156, verified).
  - Ограничить `ap.queue` и `eth_rx` примерно 64 кадрами: выбрасывать старейший и считать выброшенные.
- `cli`, около 35 строк.
  - Проверять `--net`: сейчас любое значение, кроме `nat`/`user`, молча превращается в `none` (lib.rs 119, 270, 332).
  - `bridge:PATH` либо подключается, либо выходит с понятной ошибкой.
  - `--hostfwd` вместе с bridge отклоняется.
  - Счётчики печатаются в конце.
- Тесты, около 150 строк.
  - Кадрирование через `UnixStream::pair` с поддельным демоном.
  - Фильтр.
  - Beacon при 1000 кадров в очереди.
  - Ограничение очереди.
  - Переподключение.
  - `cargo check` под wasm.
  - Новых crates нет.

### 4.2 `tools/twin/twin.py` (AnimatedPixelClock-twin)
- `--lan` превращается в `--net bridge:/var/run/socket_vmnet.bridged.en0`. `--hostfwd` при этом не передаётся, `--mac 02:54:57:49:4E:01` остаётся как сейчас, `--web` на 127.0.0.1 не затрагивается.
- Перед запуском три проверки:
  1. Сокет существует и подключается. Если нет, `twin.py` печатает команды из §3 и выходит.
  2. **Домашний guard.** IP и MAC шлюза по умолчанию (`route -n get default`, `arp -n`) совпадают с `~/twin/state/lan.txt`. Файл лежит вне публичного репозитория и пишется командой `twin.py lan-setup` дома. Так твин не выйдет в чужую сеть: демон бриджит любую сеть, в которой сейчас `en0`.
  3. Имя начинается с `TWIN-`.
- `tools/twin/lanprobe.py`, около 60 строк, для проверки A1. Через тот же сокет отправляет один DHCPDISCOVER: `chaddr` = MAC твина, option 61, option 12 `TWIN-…`, broadcast-флаг. Ждёт OFFER и печатает `yiaddr`, маску, router и server-id. REQUEST не отправляет, поэтому аренда не оформляется.

### 4.3 Имя с префиксом TWIN-
Имя задаёт прошивка, а не движок. `deviceName` уходит в DHCP option 12 и становится mDNS-хостом (network.cpp 52-73). Правило имени: 1–31 символ, первый символ — буква, дальше буквы, цифры и `-` (web.cpp 689-698, прочитал, verified).

Предлагаю `TWIN-NickoScopeMatrix-64x128-01`. Это ровно 31 символ, в пределах лимита. Имя настоящей панели взято из памяти проекта. Подойдёт и любое более короткое `TWIN-…`.

Задаётся один раз до первого запуска в сети: `twin.py rename <name>` в обычном NAT-режиме через `127.0.0.1` hostfwd на обработчик rename. Маршрут `/api/rename` известен по исследованию `alias`, сам маршрут я не открывал. Затем перезапуск твина, потому что hostname берётся при инициализации Wi-Fi (**не проверено**, отсюда перезапуск).

## 5. Запасные пути

- **№1: проводной USB- или Thunderbolt-Ethernet адаптер.** Нужен, если A0 не проходит (Wi-Fi-мост на N1 не работает) или владельцу нужен настоящий свой MAC и в эфире. Тот же `socket_vmnet bridged`, в plist `en0` заменяется на `enX` по README: `sed s@en0@${BRIDGED}@g`. Код движка тот же, меняется только путь сокета. MAC-NAT включается только для Wi-Fi-станции (if_bridge.c 2966-2972, verified), поэтому на проводе MAC твина настоящий.
  - Нужно железо и кабель к месту, где стоит Mac: встроенного Ethernet у Mac17,9 нет (verified).
  - `enX` должен появиться в `vmnet_copy_shared_interface_list()`.
  - Mac получит второй адрес в той же сети, если адаптер не оставить без IP.
  - Ничего из этого не проверено.
- **№2: только программный путь — `/32`-алиас на `en0`.** Своего MAC нет даже в DHCP: DHCP вообще нет, адрес статический.
  - Владелец ставит root-LaunchDaemon, который раз в 30 с выставляет `ifconfig en0 inet TWIN_IP netmask 255.255.255.255 alias` с тем же домашним guard. Нужен цикл, а не разовый запуск: IPConfiguration один раз вычищает чужие адреса после первого DHCP-publish (bootp-534.100.6 ipconfigd.c 3313-3365, verified).
  - Движок: режим `--net alias:` с bind-before-connect (нужен `socket2`), `0.0.0.0:80` с фильтром по `local_addr` (конкретный адрес на порту ниже 1024 без root даёт EACCES, проверено тестом), mDNS через `dns_sd` (`DNSServiceRegisterRecord`).
  - Минусы: 200–230 строк кода, работают только перечисленные порты, адрес надо выбрать вне пула eero (пул не проверен), wildcard-сервисы Mac (5000, 7000, 17500) становятся видны на `TWIN_IP`.
  - **Обязательная доработка в этом режиме:** запрет в NAT на назначения `127/8`, `169.254/16` и собственные адреса Mac. В `nat.rs` фильтра по назначению я не нашёл, так что гость, по-видимому, может достучаться до loopback-сервисов Mac. Тестом не проверено. Если гость доступен из LAN через Lua или OTA, это готовая точка входа.
- Отвергнуты:
  - `vmnet` напрямую из движка: root при каждом запуске или недоступный entitlement.
  - Shared mode и `vmnet_network` в macOS 26: только NAT, bridged не поддерживается (verified).
  - Самодельный мост на BPF: `/dev/bpf*` принадлежит root, пришлось бы менять права на устройства.
  - `hostfwd` на `0.0.0.0`: адрес остаётся адресом Mac. Годится только как временная мера.

## 6. Безопасность

1. **HTTP API без аутентификации, как у настоящей панели.** Любой хост в сети может переименовать твин, менять настройки, загружать Lua и прошивку через OTA. Lua и OTA проверены на твине, см. `cabb644`. По сути, это выполнение произвольного кода гостя для всей сети, и так задумано прошивкой. Разница с железом: у настоящей панели такой код заперт в микроконтроллере, а у твина за гостем стоит только эмулятор. Он работает от пользователя `apple` с доступом к его домашнему каталогу, а нативный JIT содержит `unsafe` (15 вхождений в `xtensa-lx7/src/jit/mod.rs`). Проектировался ли esp32sim как граница безопасности — **не проверено**; считать, что не проектировался. Меры:
   - держать твин в сети только на время испытаний и не запускать его постоянно;
   - домашний guard;
   - замерить `--no-jit` (флаг есть, lib.rs:169, 461) и перейти на него в режиме LAN, если интерпретатор держит реальное время (скорость **не измерена**);
   - не класть во флеш твина боевые учётки MQTT. Если MQTT нужен, завести отдельного пользователя брокера.
2. **Мост снижает часть рисков.** Трафик гостя больше не идёт через сокеты Mac, поэтому путь «гость → NAT → loopback Mac» пропадает. Сервисы Mac на IP твина тоже не видны: это не адрес Mac, в отличие от алиаса.
3. **Сокет `socket_vmnet` (`root:staff 0770`).** Любой процесс пользователя `apple` может отправлять в LAN и принимать из неё сырые L2-кадры, включая ARP-заявки на чужие IP, например на шлюз. Без демона для этого нужен root: `/dev/bpf*` имеет права `crw------- root:wheel`, verified. Демон пересылает кадры клиентов без фильтрации (verified). Пропустит ли MAC-NAT ARP-заявку на чужой IP, по коду похоже на «да», но тестом **не проверено**. На однопользовательском Mac это принимается как цена решения. Если нужно строже — `bootout` демона, пока твин не в работе.
4. **Сам демон.** Он постоянно работает от root и постоянно держит мост на `en0` в любой сети, где находится ноутбук. Бинарник ставится из тарбола с проверкой attestation в `/opt` с владельцем root.
5. **Путаница в сети.**
   - Утилиты агента при двух панелях требуют явного выбора (`ChoiceNeeded`), это безопасно.
   - HA через zeroconf может предложить обнаруженное устройство, если какая-то интеграция совпадёт по `_http._tcp`, — **не проверено**.
   - Широковещательные пакеты на UDP 4210, если такие вообще кто-то отправляет, получат обе панели — **не проверено**.
   - IP-трекеры HA на основе ARP увидят за IP твина MAC Mac.

## 7. Приёмка (по порядку; каждый пункт — шлюз к следующему)

- **A0, мост поднялся.** Выполняется сразу после §3, без кода движка.
  - `ls -l /var/run/socket_vmnet.bridged.en0` показывает `srwxrwx--- root staff`.
  - В `/var/log/socket_vmnet/bridged.en0.stderr` нет ошибок vmnet.
  - `ifconfig` показывает `bridgeN` с членами `en0` и `vmenetN`.
  - Флаг MACNAT на `en0` в выводе ifconfig — **не проверено**, что ifconfig его показывает.
  - Не прошло → запасной путь №1 или №2.
- **A1, DHCP через мост.** `lanprobe.py` получает OFFER от 192.168.4.1 с `yiaddr` в 192.168.4.0/22 и маской 255.255.252.0.
- **A2, аренда у роутера.** Твин запущен с `--lan`. Консоль прошивки показывает 192.168.4.x. В приложении eero есть клиент `TWIN-NickoScopeMatrix-64x128-01` с арендой. Какой MAC eero покажет у этого клиента, твина или Mac, записать как факт — **не проверено**. Если резерв возможен: после перезапуска твина IP тот же.
- **A3, HA достаёт до твина.** С хоста HA (nickohome, Terminal/SSH): `ping` и `curl -m3 http://<twin_ip>/` отдают портал. `arp -an` показывает за этим IP MAC Mac — так и должно быть при MAC-NAT, это не дефект. Интеграции в HA не создаём.
- **A4, `discover.py`.** На Mac и на nickohome (avahi) выдаёт две панели: `90:E5:B1:D2:0E:2C` на .89 и `02:54:57:49:4E:01` на новом IP. `discover.py --mac 02:54:57:49:4E:01` печатает IP твина с кодом 0, `--mac 90:E5:B1:D2:0E:2C` по-прежнему .89.
- **A5, настоящая панель не задета.** .89 отвечает, её сущности в HA не изменились, `panel.py --mac 90:E5:B1:D2:0E:2C` работает.
- **A6, устойчивость.**
  - 25 мин без обращений (больше 20-минутного таймаута MAC-NAT), затем `curl` с HA проходит.
  - 60 с непрерывного опроса HTTP — твин не отваливается (проверка beacon-фикса).
  - Сон и пробуждение Mac, переподключение Wi-Fi: `reconnects` растёт, связь возвращается. Если нет — зафиксировать, что помогает `sudo launchctl kickstart -k` (#130).
- **A7, guard.** С неверным `lan.txt` или вне дома `twin.py --lan` отказывается запускаться.
- **A8, Mac → твин.** `curl http://<twin_ip>/` с самого Mac — **не проверено**. Если не работает, портал открываем с другого хоста, панель — через `--web`.
