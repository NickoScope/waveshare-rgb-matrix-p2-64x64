# Why the portal freezes: reproduced, with the panel's own words

2026-09-20, firmware 2.4.0 `26a1be4`, panel at 192.168.4.62, USB attached so serial was readable.
The owner's report: *"очень часто управление виснет, пока не нажмешь ресет"*.

**It is reproduced, the mechanism is named, and the firmware never crashes - which is exactly why
only a reset appears to fix it.**

## What happens

A browser opening the portal does not make one request. It makes six to twelve at once: `/`,
`/portal.css`, `/portal.js`, `/api/portal`, `/api/status`, `/api/info`, and then keeps polling.
The panel's web server is synchronous - it serves them one at a time - so the rest sit queued in
lwIP, each holding its own buffers in **internal** RAM, of which the board has about 34 KB free.

Driving exactly that pattern (12 concurrent requests, a round a second) the panel said this on
serial:

```
09:04:43 [mem] internal minimum 8784 -> 7232 B during web server (free 26260, largest 9204, tasks 13)
09:04:43 [mem] allocation failed: 1626 B, caps 0x80c, task wifi, 20 so far, before web server
09:04:48 [loop] web / took 4224 ms
09:04:48 [loop] web server took 4224 ms
09:04:48 [mem] allocation failed: 1626 B, caps 0x80c, task wifi, 25 so far, before web server
09:05:41 [mem] allocation failed: 12288 B, caps 0x804, task loopTask, 26 so far, before yacht radar
09:05:44 [loop] mqtt took 1001 ms
09:05:54 [loop] mqtt took 1001 ms
09:06:14 [loop] mqtt took 1001 ms
```

Read in order:

1. Internal free RAM falls to **7,232 B**, the largest contiguous block to 9,204 B.
2. The **Wi-Fi task** cannot allocate its **1,626-byte DMA buffers** (`caps 0x80c` =
   internal + 8-bit + DMA) - **25 failures in eleven seconds**. Those are the buffers packets
   arrive in. Without them, packets are dropped.
3. One `GET /` takes **4,224 ms**.
4. The panel goes off the network entirely. It did not answer for **over 90 seconds** - the test
   gave up; it came back on its own after three to four minutes.
5. **The firmware never crashed.** Serial kept printing the whole time, the clock kept running on
   the screen. Only the network was wedged - `mqtt` then blocks for exactly 1,001 ms every time,
   which is its one-second timeout failing over and over.

That last point is the whole answer to the owner's question. Nothing looks broken: the panel is
lit, the clock ticks. Only the portal is gone, and it stays gone for minutes, so a reset looks
like the cure.

## The second family: things that block loop() on their own

The web server runs inside `loop()`. Anything else slow in `loop()` freezes the portal for as long
as it runs, with no memory problem at all. From the same session's serial, with nothing being
stressed:

| What | Worst seen | How often |
|---|---|---|
| `tetris_clock` one frame | **286.4 ms** | every frame it happens on, style shown 60 s |
| `snake_clock` one frame | **179.9 ms** | as above |
| `snooker_clock` opening | **325.4 ms** | each time the style comes round |
| `mqtt` | **528 ms** (1,001 ms once wedged) | seen three times in ten minutes |
| the market page | 204 ms | while it refreshes |

The clock styles rotate every 60 seconds, so a quarter-second freeze arrives on its own schedule
all day. A click that lands in one of those windows feels like the portal ignoring it.

## Other defects found in the same session

- **The weather has never succeeded this boot** (`weatherValid: false`, no `weatherAgeSeconds`).
  It retries every 60 s (`WEATHER_RETRY_INTERVAL_MS`), and each retry is a TLS handshake -
  `WiFiClientSecure` with mbedTLS buffers in internal RAM, the same RAM the Wi-Fi task needs.
  A fix already exists unmerged on `feat/tls-buffers-psram` ("allocate mbedTLS buffers in PSRAM").
- **The yacht radar failed to allocate 12,288 B** of internal RAM under the same pressure
  (`caps 0x804`, task `loopTask`).
- **`/api/ir/sim` silently does nothing** and still answers `{"success":true}`. The IR receiver is
  `"not built"` and `enabled:false` in this build, so a page walk driven through it moves no pages -
  it cost this session a whole sweep before that was noticed. An endpoint that cannot act should
  say so.

## What would fix it, in order of value

1. **Cap how many connections the web server accepts at once**, or serve the portal's assets in a
   way that does not leave ten sockets queued. This is the root of the first family and the only
   one that stops the wedge.
2. **Keep a reserve of internal RAM the web path may not touch**, so the Wi-Fi task's 1,626-byte
   buffers always exist. A dropped page is an inconvenience; a dropped radio is a reset.
3. **Merge the TLS-buffers-in-PSRAM work** and find out why the weather fails, so the panel stops
   doing a handshake a minute for nothing.
4. **Bound the Lua clock styles' per-frame work**, or draw them in slices, so no frame costs a
   quarter of a second.
5. **Give MQTT a shorter timeout** so a dead broker cannot cost a second per pass.

## What this does not yet cover

Audio and video effects, the animation player, and the remaining pages were not reached in this
session - the page walk was driven through `/api/ir/sim`, which turned out to do nothing. They need
a working way to change pages over HTTP first.
