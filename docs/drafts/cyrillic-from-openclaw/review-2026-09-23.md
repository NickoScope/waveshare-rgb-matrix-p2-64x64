# Review of the ledmatrix agent's Cyrillic plan, against sources (2026-09-23)

Question from the owner: is "Cyrillic as a second font, not an extension of the Latin one" right? What do the sources and mature libraries do?

## Facts, each from a source read this session

| Fact | Source |
|---|---|
| `GFXfont.first/last` are `uint16_t`; the glyph lookup is `glyph[c - first]` over one contiguous range | Adafruit GFX 1.12.6 as built, `gfxfont.h` lines 21-26, `Adafruit_GFX.cpp` 1438/1524 |
| Adafruit's own text path is 8-bit: `write(uint8_t)`, and `first/last` are read with `pgm_read_byte` | `Adafruit_GFX.h:194`, `Adafruit_GFX.cpp:1499, 1522-1523, 1638-1639` |
| PicopixelFB covers 0x20-0x7E | `src/fonts/picopixel_fb.h:50` |
| Bridging to U+045F in one table means 0x7F..0x3FF, 897 empty slots, about 7 KB of flash at 8 B per glyph entry | arithmetic on the above |
| AWTRIX 3 (an ESP32 matrix clock, like ours) uses one GFXfont 0x20-0xFF and remaps UTF-8 Cyrillic into the 0x80-0xFF slots with `utf8ascii()`; Polish letters are folded to plain Latin | `Blueforcer/awtrix3` `src/AwtrixFont.h:518-521`, `src/Functions.cpp:147+` |
| U8g2 keeps one font with a Unicode lookup table for codes above 255, decodes UTF-8 in `drawUTF8`, and draws nothing for a missing glyph | DeepWiki on `olikraus/u8g2` (u8g2_font.c, u8x8_utf8_next); not read line by line |
| LVGL keeps one font with several cmaps (FORMAT0 for dense ranges, SPARSE with binary search) | DeepWiki on `lvgl/lvgl` (lv_font_fmt_txt.c); not read line by line |
| TFT_eSPI decodes UTF-8 itself; GFX fonts are still range-limited; its smooth fonts look up any 16-bit code and draw a box for a missing one | DeepWiki on `Bodmer/TFT_eSPI`; not read line by line |

## Verdict on the plan

- "900 empty codes" is right (897). "One table would bloat" is true but small here: about 7 KB on a 32 MB board. Size is not the real reason to split.
- The real reason is the one the plan also gives: Adafruit's `print()` cannot carry a code above 255 at all, so Cyrillic needs our own decoder and drawing path whichever table layout is chosen.
- Two GFXfonts routed by range is a hand-made two-entry cmap, the same idea as LVGL's cmaps and U8g2's Unicode table. It is sound for two ranges.

## The option the plan did not weigh

The AWTRIX way: one font 0x20-0xFF, Cyrillic placed in 0x80-0xFF, and a UTF-8 remap at the input. Its advantage for us is that every existing loop and even `display.print()` work unchanged once a string has been converted. Its costs: 256 codes in total, a private encoding to keep in sync in the firmware, luasim and every tool, and no room for a third script.

## Gaps in the plan, by common practice

1. Unknown or malformed input becomes a space. Mature libraries either draw a visible box (TFT_eSPI) or skip (U8g2); the Unicode Standard's recommendation is U+FFFD. A visible "missing" glyph shows the bug instead of hiding it. (Unicode chapter 3 not re-read this session.)
2. The 2-byte decoder accepts overlong forms (C0/C1 leads). Reject them.
3. U+0400-045F slots that are not drawn (Ukrainian, Serbian and so on) must point at the missing glyph, not at garbage.
4. Width functions and drawing must share one decoder, or centred text drifts: the plan says so, keep it.

## Recommendation

Keep the plan's shape (second range, one shared decoder and drawing helper for Lua and C++, luasim in step), and add the missing-glyph box and strict decoding. Choose the AWTRIX remap only if touching every `print()` call proves too invasive. Either way the 3-pixel shapes are decided on the wall, not in a table.
