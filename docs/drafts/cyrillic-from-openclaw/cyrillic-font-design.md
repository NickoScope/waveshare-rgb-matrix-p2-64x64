# Кириллица как системный шрифт PicopixelFB — план-патч

Прошивка `NickoScope/AnimatedPixelClock`. Флеш делает Николай; здесь — дизайн, патч по файлам, источник глифов, бюджет и чек-лист.

## 0. Как оно устроено на самом деле (проверено по коду)

- `GFXfont = {bitmap*, GFXglyph*, uint16 first, uint16 last, uint8 yAdvance}`. Поиск глифа — **`glyph[cp - first]` по ОДНОМУ непрерывному диапазону.** Расширить `PicopixelFB.last` с 0x7E до кириллицы нельзя: между 0x7E и 0x410 — 900 пустых слотов.
- `GFXglyph = {uint16 bitmapOffset, uint8 w, h, xAdvance, int8 xOffset, yOffset}` = 7 байт (в массиве 8 с выравниванием). Битмап — непрерывный поток MSB-first, row-major (gy внешний, gx внутренний), каждый глиф байт-выровнен по своему offset.
- `PicopixelFB` переиспользует **штатную** таблицу `PicopixelGlyphs` (только битмап свой — ради плоского U).
- **Каждое место рисования текста катает свой цикл** по этим таблицам, а не через Adafruit:
  - `src/lua/lua_px.cpp` — `glyphFor()/l_text/l_width` (путь px.text). ASCII 0x20–0x7E, складывает регистр (стр. 202–205).
  - `tools/luasim/luasim.c` — **эталон fx_parity**, отдельная копия того же цикла; шрифт в `font_picopixel.inc`, который генерит `tools/luasim/gen_font.py` из `picopixel_fb.h`.
  - `src/worldclock/worldclock.cpp` (`drawName`), `src/flightboard/flightboard.cpp` (`flightboardNameWidth` + цикл рисования) — свои копии `glyphFor`.
  - **Adafruit `display.print()`** через `setFont(&PicopixelFB)`: `cards`, `media_page`, `market_page/pico`, `railboard`, `yachtradar`, `clock_style`, `lua_effects`. Тут `write(uint8_t)` — **принципиально не умеет UTF-8 и коды > 255**.

Отсюда два вывода, которые определяют весь патч:
1. Кириллица — это **второй `GFXfont` рядом**, не расширение первого.
2. UTF-8 нужно декодировать **до** Adafruit; штатный `print()` для кириллицы не используем — заводим общий хелпер.

## 1. Глифы: PicopixelCyr (второй GFXfont)

Второй шрифт на блок **U+0400–U+045F** (96 слотов; покрывает Ё=0x401, А–я=0x410–0x44F, ё=0x451, и оставляет место под Ї/Є/і потом). Геометрия ровно как у латиницы: 5 строк, чернила на строках базовой линии +2..+6 (`yOffset -4`), `xOffset 0`, `advance = width + 1`.

**Регистр складываем**, как латиница в `lua_px.cpp:202`: строчные 0x430–0x44F и ё указывают на тот же `bitmapOffset`, что и прописные. 3×5 всё равно не держит различимые заглавные/строчные, а панель и так фолдит `a→A`. Итог — ~33 формы в битмапе, но таблица из 96 слотов маршрутизирует строчные на прописные **за 0 лишних байт**.

**Источник глифов: оригинальный набор**, нарисованный под конструкцию Picopixel (тот же штрих, что у латинских А/Е/К/М/О/Р/С/Т/Х/В, которые совпадают по форме). Готового BSD-набора 3×5 кириллицы под Picopixel нет; матчить чужой шрифт к «плоскому U» неправильно. **Лицензия — та же BSD, что у Adafruit GFX и остального репо.** Набор лежит в генераторе `mkcyr.py` (приложен), одним ASCII-источником, откуда пакуется и заголовок, и `.inc` для симулятора — чтобы прошивка и эталон не разошлись.

Широкие буквы (Ж М Ф Ш Щ Ы Ю) — 5px, Ъ — 4px, остальные 3px; per-glyph width в формате это позволяет. Диагональные (И Й Л Д У) — известно трудные на 3px; в наборе первый заход, финально глазами на стене (панель важнее таблицы) и правится прямо в `mkcyr.py`.

Генератор запускается:
```
python3 mkcyr.py --header  > блок для picopixel_fb.h
python3 mkcyr.py --inc     > блок для font_picopixel.inc
python3 mkcyr.py           > статистика байт
```
Пакует битово-точно под цикл `l_text` (проверено: `bo++`, `(7-(bit&7))`).

## 2. Точки правки по файлам

### 2.1 `src/fonts/picopixel_fb.h` (+ вставка из `mkcyr.py --header`)
После определения `PicopixelFB` дописать `PicopixelCyrBitmaps[]`, `PicopixelCyrGlyphs[]`, `PicopixelCyr` и **общий UTF-8 хелпер**, чтобы все места рисования звали одно:

```c
// UTF-8 -> codepoint; двигает *p. Наш диапазон: ASCII 1 байт, кириллица 2 байта.
static inline uint32_t pxfbNextCp(const unsigned char **p) {
  uint32_t c = **p;
  if (c < 0x80) { (*p)++; return c; }
  if ((c & 0xE0) == 0xC0 && ((*p)[1] & 0xC0) == 0x80) {  // 2-байтовые: сюда попадает 0x400–0x7FF
    uint32_t cp = ((c & 0x1F) << 6) | ((*p)[1] & 0x3F); *p += 2; return cp;
  }
  (*p)++; return 0x20;   // 3/4-байтовые и мусор -> пробел, латиница нетронута
}

// Один глиф + из какого шрифта его бит-массив. Возвращает &font и &glyph.
static inline const GFXglyph *pxfbGlyph(uint32_t cp, const GFXfont **font) {
  if (cp >= 0x0400 && cp <= 0x045F) {              // кириллица: регистр УЖЕ сложен в таблице
    *font = &PicopixelCyr;
    return &PicopixelCyrGlyphs[cp - 0x0400];
  }
  *font = &PicopixelFB;                            // латиница: складываем как раньше
  if (cp >= 'a' && cp <= 'z') cp -= 32;
  if (cp < PicopixelFB.first || cp > PicopixelFB.last) cp = ' ';
  return &PicopixelFB.glyph[cp - PicopixelFB.first];
}
```
Обратная совместимость: латинская ветка байт-в-байт прежняя (тот же фолд `a→z`, тот же `space` для вне-диапазона).

### 2.2 `src/lua/lua_px.cpp` — px.text / px.width
Заменить `glyphFor(unsigned char)` и оба цикла `for (c=s; *c; c++)` на декодер:

- `l_text` (стр. 216–228): цикл по `pxfbNextCp(&c)`; `const GFXfont *f; const GFXglyph *gl = pxfbGlyph(cp, &f);` дальше существующее рисование, но битмап читать `f->bitmap[...]`, а `base` считать от `f->yAdvance` (у обоих 7 — совпадает). Проверку `x >= W` оставить.
- `l_width` (стр. 232–238): та же замена, суммировать `gl->xAdvance`.
- Старую `glyphFor` (стр. 201–206) удалить — её роль у `pxfbGlyph`.

Латиница остаётся точной; кириллица начинает рисоваться в **любом** Lua-эффекте через px.text/px.width.

### 2.3 `tools/luasim/luasim.c` + `gen_font.py` (ИНАЧЕ РАЗЪЕДЕТСЯ fx_parity)
Эталон обязан рисовать тем же:
- `gen_font.py`: дописать вызов `mkcyr.py --inc` (или встроить ту же генерацию), чтобы `font_picopixel.inc` нёс `kPicoCyrBitmap[]`/`kPicoCyrGlyphs[]` и `PICO_CYR_FIRST/LAST`.
- `luasim.c` `l_text`/`l_width` (стр. 140–176): тот же UTF-8-декод и маршрутизация на `kPicoCyrGlyphs[cp-0x400]` vs `kPicoGlyphs[cp-0x20]`, с тем же фолдом латиницы. Форма кода 1:1 с `pxfbGlyph`.

### 2.4 C++-страницы
- **Свои циклы** (`worldclock.cpp` `drawName`/`glyphFor` стр. 130–158; `flightboard.cpp` `flightboardNameWidth` стр. 243–251 и цикл рисования ~716): заменить на `pxfbNextCp`+`pxfbGlyph`, читать `f->bitmap`. Дублирующиеся локальные `glyphFor` удалить.
- **`display.print()`-страницы** (`cards`, `media_page`, `market*`, `railboard`, `yachtradar`, `clock_style`, `lua_effects`): для **пользовательских динамических строк**, которые могут быть кириллицей (название трека в media, текст карточки в cards, имена в railboard), заменить `display.print(s)` на новый `pxfbDrawText(display, x, y, s, col)` (тонкая обёртка над циклом из 2.2, рисующая через `display.drawPixel`). Статичные англоязычные подписи не трогаем. Это точечно, не глобально.

Рекомендую положить `pxfbDrawText()` и `pxfbTextWidth()` прямо в `picopixel_fb.h` (шаблон по `Adafruit_GFX&`) — тогда все восемь мест и Lua зовут один код, и копии `glyphFor` исчезают из репо.

## 3. Бюджет и риски

- **Флеш:** битмап 81 B + таблица 96×8 ≈ 768 B ⇒ **~0.85 КБ**. На фоне многомегабайтного образа — шум.
- **SRAM/RAM: 0.** `PROGMEM` остаётся во флеше, рисование читает по байту. Узкое место (~19–24 КБ внутренней SRAM) **не трогается вообще** — это главный ответ на опасение по памяти.
- **Стек:** декодер добавляет пару локальных `uint32_t`, без рекурсии. 12 КБ стека Lua-задачи в безопасности.
- **Такт кадра:** не меняется — кириллица идёт тем же путём Lua→C, что латиница; лишних пересечений границы нет.
- **Риск №1 — расхождение э**талона: если поправить прошивку и забыть `luasim.c`/`gen_font.py`, fx_parity даст ложные диффы. Правятся вместе (раздел 2.3).
- **Риск №2 — `mkbdf.py`/chafa:** в `mkbdf.py` добавить `if code >= 0x80: continue`, чтобы кириллица **не** попадала в BDF — иначе la_gioconda/фото-в-ASCII начнёт матчить кириллические формы к латинским фото. Кириллицу из chafa-конвейера намеренно исключаем.
- **Риск №3 — легибельность 3px:** И Й Л Д У Ж Щ на 2 мм под эпоксидкой. Проверять глазами, не по PNG.

## 4. Что тестировать через fx_parity

1. `python3 tools/luasim/gen_font.py` — `.inc` содержит кириллический блок.
2. Собрать `luasim`, собрать прошивку (sim-таргет).
3. Тест-эффект: `px.text(2, 8, "ПРИВЕТ МИР 2026", 255,255,255)` + `px.text(2, 20, "привет ёжик", ...)` + смешанная `"WiFi: Кухня"`.
4. `fx_parity.py` на этом эффекте — **0 расходящихся пикселей** симулятор↔эталон.
5. `px.width("ПРИВЕТ") == px.width("привет")` (фолд регистра) и суммарная ширина = сумма advance.
6. Регресс латиницы: `fx_parity` на существующих галерейных скриптах — без диффов (латинская ветка не изменилась).
7. На железе (Николай): worldclock с кириллическим именем панели, media с русским названием трека.
